# 今日待办模块整改方案

> 版本：v1（待评审） · 日期：2026-08-24
> 范围：Bug 修复（编辑 / 删除复活）、完成历史、待办模块整体设计、服务端存储打通

---

## 一、问题诊断（先说根因）

### 问题 1：添加后无法编辑 —— 功能缺失

`StoreContext` 只有 `addTodo / toggleTodo / removeTodo` 三个动作，**从头到尾就没有 `updateTodo`**，UI 上也没有任何编辑入口。不是 bug，是压根没做。

### 问题 2：删除后又出现 —— 同步协议的「删除无法传播」缺陷（严重）

这是最重要的发现。当前同步链路是「全量快照 + 按 `updatedAt` 的并集合并」，删除操作在这个模型下**天然无法传播**：

```
本地删除 todo（数组里 filter 掉）
  → push 全量快照（不含该 todo）到服务端
  → 服务端 mergeSnapshot(remote, body)：remote 有、body 没有 → 保留   ← 问题在这
  → 返回合并后的快照（仍含该 todo）
  → 前端 applyRemote 再做一次并集合并 → 已删除的 todo 复活
```

`mergeByUpdatedAt` 的语义是「**两边出现的 id 取并集，同 id 比 updatedAt**」——「本地没有」被解释为「本地新增了一个不存在的东西」，而不是「本地删除了它」。服务端与前端两份 merge 函数（`server/lib/merge.mjs` 和 `src/lib/sync.ts`）行为一致，所以两边都会复活数据。

**⚠️ 波及范围不止待办**：`requirements` 和 `projects` 走的是同一套 merge 函数，删需求、删项目同样会复活。你之所以只在待办上发现，是因为待办删得最频繁。这个修复必须三个实体一起做。

### 问题 3：完成历史看不到 —— 数据在，但没有视图

历史待办**其实一直都在**（localStorage 和云端快照都没清理过），只是 UI 只渲染 `t.date === today` 的条目，任何页面都没有按日期回看的能力。另外 `TodoItem` 没有 `completedAt` 字段，只有 `done` 布尔值，无法回答「这条是几点完成的」。

### 关于「打通接口存储到服务端」

一个需要澄清的事实：**待办目前已经随全量快照同步到服务端了**（`POST /api/push` 的 payload 里就有 `todos`）。真正的问题不是「没存」，而是**删除语义坏了 + 历史无入口**。所以方案选型的关键是：修好现有通道，还是另起一套独立接口。

## 二、方案选型

| 维度 | 方案 A：修复现有快照同步（墓碑软删）✅ 推荐 | 方案 B：独立待办 REST API + SQLite 表 |
|---|---|---|
| 思路 | 删除改为软删除（打 `deletedAt` 墓碑），墓碑作为普通条目参与现有 LWW 合并，UI 层过滤；待办继续走快照通道 | 服务端新建 `todos` 表，提供 `GET /api/todos?from=&to=`、`POST`、`PATCH`、`DELETE` 细粒度接口，待办脱离快照体系 |
| 服务端改动 | merge.mjs 加 10 行墓碑清理；无新表、无新路由 | 建表 + 5 个 CRUD 路由 + 迁移脚本（把快照里的 todos 搬进表） |
| 离线可用 | ✅ 本地优先架构保持不变，断网照常用 | ❌ 需要重新设计离线队列/重试/冲突 |
| 多端同步 | ✅ 一套机制覆盖 requirements / todos / projects（顺手修掉全部删除复活 bug） | ❌ 两套同步逻辑并存，同一份数据两个真相源 |
| 数据规模适配 | 待办一年千条级，快照体积完全可控 | 按需分页拉取，但这个量级用不上 |
| 工作量 | 小（约 1 个开发批次） | 大（3~4 倍） |
| 后续扩展 | 提醒推送等实时能力时再演进 | 天然支持 |

**结论：选 A。** 这是单人/小团队工具，快照通道的体积和性能绰绰有余；B 的细粒度收益在这个规模下兑现不了，代价却是双通道真相源 + 离线逻辑重做。等以后真有「服务端主动推送提醒」这类需求时，再在服务端把 todos 从快照拆到独立表也不迟（本方案的数据模型向前兼容这条演进路径）。

## 三、数据模型改动

```ts
export interface TodoItem {
  id: string
  content: string
  /** 目标日期 yyyy-MM-dd */
  date: string
  done: boolean
  /** 完成时间 ISO：勾选时写入，取消勾选清除（历史页/统计用） */
  completedAt?: string
  /** 优先级，缺省 normal */
  priority?: 'low' | 'normal' | 'high'
  /** 关联需求 id（从今日节点一键生成待办时自动带上，可跳转） */
  requirementId?: string
  /** 软删除墓碑 ISO 时间（同步协议用，UI 层一律过滤） */
  deletedAt?: string
  createdAt: string
  updatedAt?: string
}
```

兼容性：全部新字段可选，旧数据（本地 localStorage、云端快照、JSON 备份）零迁移，缺字段按默认值处理。

## 四、同步协议改动（核心，三个实体一起修）

### 4.1 软删除 + 墓碑

**删除入口**（`removeTodo / removeRequirement / removeProject`）：不再从数组 filter 掉，而是：

```ts
const next = prev.map(t => t.id === id
  ? { ...t, deletedAt: nowISO(), updatedAt: nowISO() }  // 打墓碑
  : t)
```

**合并规则：墓碑天然参与现有 LWW，merge 函数几乎不用改。** 删除时 `updatedAt = now` 大于服务端旧版本 → 墓碑胜出 → 删除随下次 push 传播到服务端和其它设备。

**边界语义**（明确即可，无需特殊代码）：设备 A 删除、设备 B 在更晚时间编辑同一条 → B 的 `updatedAt` 更大，编辑胜出，相当于「删了又被改回来」——统一的「最后写赢」，可接受。

### 4.2 UI 层过滤

所有读取处统一走 helper（不直接碰原始数组）：

```ts
// src/lib/todos.ts（新增）
export const activeTodos = (list: TodoItem[]) => list.filter(t => !t.deletedAt)
```

改动点：`TodoPanel`、历史视图、`BackupModal` 计数、`ExportModal` 导出。备份文件里**保留墓碑**（恢复后删除状态不丢）。

### 4.3 墓碑物理清理（防数组无限膨胀）

在服务端 `mergeSnapshot` 和前端 `applyRemote` 收尾处统一：

```ts
// deletedAt 超过 90 天的墓碑 → 物理丢弃
const GC_DAYS = 90
```

两端清理时机不一致也无害：一端多留的墓碑会被 UI 过滤、且会在 90 天后被再次清理。

### 4.4 服务端改动清单（方案 A 全量）

| 文件 | 改动 |
|---|---|
| `server/lib/merge.mjs` | `mergeSnapshot` 收尾加墓碑 GC（约 10 行）；`test/merge.test.mjs` 补删除传播用例 |
| 其它 | **无**。无新表、无新路由、无迁移，快照结构不变 |
